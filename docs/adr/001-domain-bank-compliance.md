# ADR-001: Домен — корпоративный банк, комплаенс, кредитный анализ контрагентов

## Status

Accepted

## Context

На установочном совещании с бизнесом определён приоритетный сценарий автоматизации: поддержка кредитных и комплаенс-аналитиков при оценке контрагентов. Сценарий требует объединения двух типов данных — нормативных документов (ФЗ, внутренние политики) и финансовой отчётности компаний. Именно пересечение этих двух потоков создаёт уникальную ценность GraphRAG: связь «норма → политика → контрагент → рисковый фактор».

Для PoC доступны:
- открытый датасет финансовой отчётности компаний (2023–2024);
- синтетический срез нормативных и внутренних документов.

При переходе к MVP планируется подключение реального юридического корпуса после согласования с Дирекцией права и Службой ИБ.

## Alternatives

### 1. Промышленность (чертежи, ГОСТ, multimodal)

- Плюсы: сильная мультимодальность
- Минусы: OCR и layout parsing — отдельный сложный проект; нет готовых данных для PoC; затрудняет фокус на GraphRAG

### 2. Юридическая база без финансового контура

- Плюсы: нормативный корпус хорошо ложится на граф
- Минусы: слабее история про RBAC на внутренних методиках; нет дифференциации ролей `analyst` / `risk_manager`

### 3. Банк: нормативка + финансы контрагента (выбрано)

- Плюсы: пересечение ФЗ-152, RBAC, GraphRAG; понятный user journey; наличие открытых финансовых данных; естественные бизнес-роли
- Минусы: нужно связать два типа данных в одном графе знаний

## Decision

Домен: **корпоративный банк**, сценарий **кредитного / комплаенс-аналитика** при оценке контрагента. Данные на PoC: открытая финансовая отчётность + синтетический юридический срез. На MVP: реальный нормативный корпус.

## Consequences

**Плюсы:** закрывает требования банковского регулирования (ЦБ РФ, ФЗ-152); естественные роли для RBAC-демонстрации.

**Минусы:** юридический корпус на PoC упрощён — синтетические документы.

**Риски:** полный реальный нормативный корпус требует согласования с ИБ — снижается явным этапом согласования в дорожной карте MVP.

## Compliance & Security

Внутренние методики и «закрытые» политики моделируются через поля `security_level` и `allowed_roles` на фрагментах. Реальные персональные данные в PoC не используются.
