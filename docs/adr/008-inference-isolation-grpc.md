# ADR-008: Изоляция inference-слоя в выделенные GPU-сервисы (gRPC)

## Status

Accepted

## Context

Вычисление эмбеддингов и cross-encoder reranking — CPU/GPU-интенсивные задачи. Если выполнять их в процессе FastAPI, возникают два системных дефекта:

- **Блокирующий прогрев.** Синхронная загрузка весов модели (например, `SentenceTransformer`) в lifespan-обработчике FastAPI блокирует основной поток веб-сервера на несколько секунд во время инициализации PyTorch.
- **GIL и лавинообразная latency.** Векторизация и cross-encoder scoring выполняются на CPU в том же процессе. Из-за глобальной блокировки интерпретатора Python (GIL) параллельные пользовательские запросы блокируют друг друга, что приводит к нелинейному росту latency и тайм-аутам под нагрузкой.

MVP позиционируется как production-ready (almost-production), поэтому API-шлюз должен оставаться строго **I/O-bound** и масштабироваться независимо от тяжёлых вычислительных моделей. Генерация LLM уже изолирована в vLLM (ADR-003); по тем же причинам необходимо изолировать embeddings и reranker.

## Alternatives

### 1. In-process инференс в FastAPI (как на PoC)

- Плюсы: минимум сервисов, простой деплой
- Минусы: блокирующий прогрев в lifespan; GIL сериализует CPU-bound инференс; latency деградирует под параллельной нагрузкой; нельзя масштабировать API и модели раздельно

### 2. Только vLLM, embeddings/reranker отдельными ad-hoc HTTP-сервисами

- Плюсы: изоляция от API; переиспользование GPU
- Минусы: разнородные протоколы и форматы; нет единого динамического батчинга; рост числа несогласованных сервисов

### 3. Выделенный inference-сервер (Triton) для embeddings + cross-encoder поверх gRPC (выбрано)

- Плюсы: единый GPU-сервер инференса с **динамическим батчингом** и конкурентными инстансами моделей; нативный **gRPC** (низкий overhead, multiplexing, стриминг); API остаётся I/O-bound; embeddings и reranker масштабируются независимо; единый формат метрик и трассировки
- Минусы: дополнительный компонент в эксплуатации; требуется упаковка моделей в Triton model repository; зависимость от GPU

## Decision

Полностью **изолировать inference-слой** от API-шлюза:

1. **Embeddings и cross-encoder reranker** выносятся в выделенный **NVIDIA Triton Inference Server** на GPU. Triton обеспечивает динамический батчинг и конкурентные инстансы моделей.
2. **Генерация LLM** остаётся в отдельном **vLLM** (ADR-003).
3. **FastAPI** взаимодействует с обоими по **gRPC** через тонкие клиенты (`Embedding Client`, `Rerank Client`, `LLM Client`) и не загружает PyTorch-веса в свой процесс. Lifespan открывает только gRPC-каналы.
4. **Batch-эмбеддинги** в Knowledge Ingestion Pipeline тоже идут в Triton (gRPC), без локальной загрузки модели.

Почему Triton, а не vLLM-only: vLLM оптимизирован под авторегрессионную генерацию, тогда как embeddings и cross-encoder — это forward-pass инференс произвольных моделей, для которого Triton даёт более гибкий батчинг, мульти-модельность и единый протокол. Связку «vLLM (генерация) + Triton (embeddings/reranker)» считаем целевой для MVP.

## Consequences

**Плюсы:** API-шлюз масштабируется независимо от моделей; стабильная latency под параллельной нагрузкой; нет блокирующего прогрева в FastAPI; единые батчинг, метрики и трассировка инференса; GPU утилизируется эффективнее за счёт динамического батчинга.

**Минусы:** дополнительный сервис (Triton) в эксплуатации; модели нужно упаковывать в формат Triton; зависимость от закупки GPU.

**Риски:** сетевой hop API → Triton добавляет задержку — снижается colocation в K8s ns `credit-ai-gpu` (GPU node pool), gRPC keep-alive и батчингом. Насыщение GPU — метрики Prometheus и алерты (ADR-007).

**Дополнительно:** vLLM и Triton размещаются в K8s namespace `credit-ai-gpu` (ADR-011); FastAPI — в `credit-ai-app`; gRPC-клиенты вместо in-process Embeddings/Reranker. ADR-007.

## Compliance & Security

Трафик app ns ↔ gpu ns остаётся внутри product K8s, защищён mTLS; секреты — Vault. Данные на VM-БД не покидают периметр банка (ФЗ-152). Трассировка `trace_id` сквозная в Jaeger.
