# ADR-000: Старт проекта — AI-ассистент кредитного аналитика

## Status

Accepted

## Context

Правление банка одобрило инициативу по внедрению AI в процессы кредитного анализа и комплаенс. Перед проектной командой поставлена задача: оценить применимость технологии GraphRAG для поддержки аналитиков при работе с нормативными документами и финансовой отчётностью контрагентов.

Банк находится на начальной стадии формирования AI-компетенций:

- **ML/AI-специалистов в штате нет.** Команда проекта состоит из разработчиков и архитекторов без опыта в машинном обучении. Проект является первым шагом в построении внутренней экспертизы.
- **Эксплуатационная команда знает только PostgreSQL.** Введение новых специализированных СУБД (Neo4j, Qdrant) требует обучения персонала и разработки операционных процедур, что целесообразно делать уже после подтверждения бизнес-гипотезы.
- **GPU-мощностей нет.** Закупка серверного GPU-оборудования требует отдельного инвестиционного решения, которое нецелесообразно принимать без подтверждённого ROI.
- **Регуляторные ограничения.** Все компоненты системы должны работать внутри закрытого контура банка — требование Службы информационной безопасности и ЦБ РФ.

В этих условиях переход сразу к полноценному production-внедрению несёт неприемлемый риск: значительные инвестиции при неподтверждённой бизнес-ценности и непроверенной архитектуре.

## Alternatives

### 1. Только архитектурная документация без реализации

- Плюсы: минимальные затраты, нет операционного риска
- Минусы: не отвечает на вопрос «работает ли»; невозможно оценить реальные ограничения; нет основания для инвестиционного решения

### 2. PoC-прототип + архитектура MVP (выбранный путь)

- Плюсы: проверяет гипотезу на реальных данных; формирует внутреннюю экспертизу; даёт Техническому комитету конкретные артефакты для GO/NO-GO
- Минусы: выше трудозатраты; часть компонентов потребует замены при переходе к MVP

### 3. Полная production-реализация с первой итерации

- Плюсы: максимальная «готовность» продукта
- Минусы: нереалистично при текущем уровне компетенций и отсутствии оборудования; размывает фокус на проверке ключевой гипотезы

## Decision

Реализовать **рабочий PoC** на ограниченном датасете с использованием имеющейся инфраструктуры (PostgreSQL, CPU-серверы) и **архитектурный проект MVP** с диаграммами, sizing и дорожной картой замены компонентов.

Все архитектурные решения фиксируются в ADR. Документация и код синхронизируются в рамках единого репозитория.

## Consequences

**Плюсы:** управляемый риск; честная позиция перед Техническим комитетом; история решений в ADR; возможность наращивания экспертизы параллельно с реализацией.

**Минусы:** часть компонентов PoC (mock LLM, pgvector вместо Qdrant, PostgreSQL вместо Neo4j) потребует замены при переходе к MVP — технический долг явно зафиксирован в ADR-007.

**Риски:** отсутствие GPU на демонстрации — снижается записью видео-демо на стенде с mock LLM и акцентом на проверенные компоненты (RBAC, GraphRAG, LangGraph pipeline).

**Дополнительно:** чеклист критериев приёмки PoC — в [docs/acceptance-criteria.md](../acceptance-criteria.md).

## Compliance & Security

Обязательства, не подлежащие компромиссу на любом этапе:

- данные и инференс — только внутри закрытого контура банка;
- внешние AI API (OpenAI, Anthropic и аналоги) не используются;
- RBAC и guardrails — не опциональные компоненты.
