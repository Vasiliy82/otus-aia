# ADR-010: Декомпозиция платформы на подсистемы и набор представлений C4

## Status

Accepted

## Context

Целевая система обслуживает один продуктовый контур — проверяемого AI-ассистента кредитного анализа, — но включает блоки с разными жизненными циклами, владельцами, рисками и SLA: online-runtime, offline-ingestion, качество/MLOps, безопасность, наблюдаемость, доставку и архитектурное управление.

Если держать всё в одной плоской границе и на одной диаграмме, модель становится нечитаемой и смешивает ответственности (runtime и data pipeline конфликтуют по нагрузке и релизам). C4 рекомендует строить отдельные представления под конкретный контекст и аудиторию, а не одну общую схему.

## Alternatives

### 1. Одна плоская система со всеми контейнерами

- Плюсы: меньше структур, быстрее на старте
- Минусы: смешение ответственностей; нечитаемые диаграммы; runtime и ingestion мешают друг другу

### 2. Дробление на множество независимых «систем»

- Плюсы: максимальная изоляция
- Минусы: избыточно для одного продукта; теряется общий продуктовый контур; enterprise-ландшафт ради ландшафта

### 3. Одна платформа + подсистемы + отдельные views (выбрано)

- Плюсы: единый продуктовый контур с явными зонами ответственности; отдельная диаграмма на каждый вопрос; легко поддерживать C1/C2
- Минусы: требует ввести понятие «подсистема» и дисциплину представлений

## Decision

Ввести единую систему **«AI-платформа кредитного анализа»** (`creditPlatform`) и выделить внутри неё **подсистемы**:

- **Secure GraphRAG Runtime** — production online-контур (FastAPI I/O-bound, vLLM, Triton).
- **Knowledge Ingestion Pipeline** — offline/batch пополнение базы знаний (вынесено из FastAPI).
- **AI Quality & MLOps** — golden set, оценка, реестр моделей и промптов.
- **Security & Access Control** — Vault, OPA, audit log.
- **Observability & Reliability** — OTel/Jaeger/Prometheus, алерты, backup/restore.

Платформенными/governance-системами в ландшафте остаются **Delivery & Release Platform** (CI/CD) и **Architecture as Code**. Внешние системы: нормативная база, источники финансовой отчётности, корпоративная IAM/SSO.

`Indexing CLI` выносится из `FastAPI Backend` в подсистему Ingestion: API обслуживает пользовательские запросы, а загрузка корпуса — отдельный контур.

Критерий «система vs подсистема»: **система** имеет самостоятельного внешнего потребителя, отдельный жизненный цикл/владельца и может использоваться вне платформы; **подсистема** нужна только платформе, но достаточно крупна, чтобы иметь свою ответственность, данные и диаграмму.

Поддерживаемый набор представлений (`architecture/mvp/views.c4`, `flows.c4`, `database.c4`, `deployment.c4`):

1. System Landscape (C1)
2. Platform Subsystems (C2)
3. Container — Secure GraphRAG Runtime
4. Container — Knowledge Ingestion Pipeline
5. AI Quality & MLOps
6. Delivery & Release Platform
7. Observability & Reliability
8. Security & Access Control
9. Architecture as Code
- плюс L3 Components, Sequence `POST /ask`, ER (PostgreSQL, Qdrant/Neo4j), Deployment.

## Consequences

**Плюсы:** читаемые диаграммы под конкретные вопросы и аудитории; явное разделение online/offline/качества/безопасности/эксплуатации; независимое масштабирование и релизы; модель показывает production, данные, качество, эксплуатацию и архитектурное управление без превращения в бесконечный enterprise-ландшафт.

**Минусы:** больше views для поддержки; нужно держать C1/C2 в актуальном состоянии.

**Риски:** рассинхрон диаграмм и кода — снижается контуром Architecture as Code (линтеры, fitness functions, сравнение as-is/to-be).

## Compliance & Security

Security & Access Control выделена отдельным представлением с trust boundaries, что упрощает ИБ-аудит. RBAC, Vault, OPA и audit log показаны явно и не смешиваются с общей контейнерной схемой.
