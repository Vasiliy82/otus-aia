# ADR-002: GraphRAG вместо простого векторного RAG

## Status

Accepted

## Context

Методичка и тема курса **не принимают** сдачу с одним vector top-k. Нарезка документов теряет ссылочную и логическую связность (норма → политика → контрагент → риск). Нужен нейро-символический контур для снижения галлюцинаций.

## Alternatives

### 1. Naive RAG (embedding + top-k)

- Плюсы: проще, быстрее в разработке
- Минусы: не соответствует требованиям курса; хуже на связных вопросах

### 2. Long-context / «весь документ в промпт»

- Плюсы: нет потери связности внутри одного файла
- Минусы: не масштабируется; дорого; не решает кросс-документные связи

### 3. GraphRAG: vector retrieve + graph expansion (выбрано)

- Плюсы: соответствует теме; объяснимый контекст; связь норма–компания–риск
- Минусы: сложнее схема и ingestion; выше latency

## Decision

Реализовать **двухшаговый GraphRAG**: (1) векторный поиск чанков в Qdrant; (2) расширение контекста по `graph_edge` из knowledge graph (PoC — PostgreSQL, MVP — Neo4j).

## Consequences

**Плюсы:** защита от «это просто RAG»; тест на graph expansion в pytest.

**Минусы:** нужна онтология и ETL в граф.

**Риски:** переусложнение онтологии — mitigated 4–5 типами узлов на PoC.

## Compliance & Security

Фильтрация RBAC выполняется **после** расширения графа, чтобы не подтянуть недоступные соседние чанки.
