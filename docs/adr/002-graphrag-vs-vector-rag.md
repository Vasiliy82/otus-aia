# ADR-002: GraphRAG вместо простого векторного RAG

## Status

Accepted

## Context

В апреле 2026 года Дирекция ИТ провела внутреннее исследование подходов к построению AI-ассистентов для работы со связанными корпоративными документами (закрытый аналитический отчёт «Сравнительный анализ RAG-архитектур для корпоративных знаний», рег. № ИТ-2026/04-07). По итогам исследования директор по информационным технологиям зафиксировал требование: система должна использовать **GraphRAG** — архитектуру с расширением контекста через граф знаний.

Ключевые тезисы, на которых основано требование:

- Нарезка документов на фрагменты при наивном RAG разрывает логические цепочки «норма → внутренняя политика → контрагент → рисковый фактор».
- Граф знаний обеспечивает объяснимость ответа: аналитик видит путь вывода, а не «чёрный ящик».
- Ссылочная целостность критична для compliance-сценариев: фрагмент вне связанного контекста может привести к неверной интерпретации нормы.

Вопрос выбора между RAG-вариантами **закрыт решением IT-директора** и данным ADR не пересматривается.

## Alternatives

### 1. Naive RAG (embedding + top-k)

- Плюсы: проще в реализации, меньше инфраструктуры
- Минусы: **не соответствует требованию Дирекции ИТ**; разрывает смысловые цепочки между документами

### 2. Long-context («весь документ в промпт»)

- Плюсы: нет потери связности внутри одного файла
- Минусы: не масштабируется на корпоративный объём; кросс-документные связи не работают; высокий расход VRAM

### 3. GraphRAG: vector retrieve + graph expansion (выбрано)

- Плюсы: соответствует требованию Дирекции ИТ; объяснимый контекст; связь норма–компания–риск; поддаётся тестированию
- Минусы: сложнее схема данных и ingestion; выше latency первого ответа

## Decision

Реализовать **двухшаговый GraphRAG** согласно требованию Дирекции ИТ:

1. Векторный поиск фрагментов через pgvector (PoC) / Qdrant (MVP).
2. Расширение контекста по рёбрам `graph_edge` из knowledge graph (PoC — PostgreSQL, MVP — Neo4j).

## Consequences

**Плюсы:** выполнено требование IT-директора; граф обеспечивает аудиторский след для compliance; graph expansion тестируется в pytest.

**Минусы:** необходима онтология и ETL-пайплайн в граф.

**Риски:** переусложнение онтологии — снижен до 4–5 типов узлов на PoC с возможностью расширения.

**Дополнительно:** обновление схемы при переходе к MVP описано в ADR-007.

## Compliance & Security

Фильтрация RBAC выполняется **после** расширения графа, чтобы не подтянуть недоступные соседние фрагменты. Требование зафиксировано в ADR-006.
