# ADR-004: Векторное хранилище — pgvector на PoC, Qdrant на MVP

## Status

Accepted

## Context

Для хранения и поиска векторных эмбеддингов фрагментов документов требуется векторная СУБД с поддержкой фильтрации по метаданным (роль пользователя, document_id).

Отдел эксплуатации банка состоит из четырёх DBA, чья экспертиза сосредоточена исключительно в **PostgreSQL** (администрирование, мониторинг, резервное копирование, DR-процедуры). Выделенного MLOps-инженера в штате нет; вакансия открыта, закрытие запланировано на Q3 2026.

Введение нового специализированного сервиса на этапе PoC означало бы:

- Обучение всей DBA-команды работе с незнакомой системой.
- Разработку новых runbook'ов и процедур DR.
- Дополнительный поверхность атаки, не прошедшая ИБ-аудит.

Риск операционного сбоя перевешивает преимущества на этапе прототипа.

## Alternatives

### 1. pgvector в существующем PostgreSQL-кластере (выбрано для PoC)

- Плюсы: нулевые операционные затраты на освоение — команда уже умеет всё; единая точка резервного копирования; нет нового сервиса в compose на PoC
- Минусы: ANN-алгоритм (IVFFlat / HNSW) слабее специализированных движков при больших объёмах; payload-фильтрация менее гибкая, чем в Qdrant

### 2. Qdrant (Docker)

- Плюсы: зрелый self-hosted движок; гибкая фильтрация payload; хорошая производительность ANN
- Минусы: **DBA-команда не знакома с Qdrant**; требует обучения и новых операционных процедур; отдельный сервис без MLOps-инженера — риск «кто это будет поддерживать»

### 3. Milvus

- Плюсы: горизонтальное масштабирование, зрелый OSS
- Минусы: значительно тяжелее в эксплуатации; тем более неприемлем без MLOps-компетенции на PoC

## Decision

**PoC:** векторный поиск через расширение **pgvector** в существующем PostgreSQL-кластере. Эмбеддинги — self-hosted embedding service (bge-m3 / sentence-transformers) на CPU.

**MVP:** переход на **Qdrant** (cluster mode) после найма MLOps-инженера (Q3 2026) и прохождения ИБ-аудита нового сервиса. Синхронизация идентификаторов фрагментов обеспечивается единым `chunk_id`.

## Consequences

**Плюсы:** нет операционного риска на PoC; команда может самостоятельно обслуживать хранилище; ускоряет старт на 2–3 недели.

**Минусы:** pgvector не обеспечит производительность при объёме >1M векторов; ограниченные возможности payload-фильтрации.

**Риски:** рассинхрон `chunk_id` между PostgreSQL и Qdrant при миграции на MVP — закрывается через единый внешний идентификатор в обоих хранилищах с первого дня.

**Дополнительно:** при переходе к MVP необходим ETL для переноса эмбеддингов из PostgreSQL в Qdrant; описан в ADR-007.

## Compliance & Security

Payload не содержит секреты вне RBAC-фильтра. Роли дублируются в поле `allowed_roles` для pre-filter запроса. pgvector работает в том же PostgreSQL-кластере, который уже прошёл ИБ-аудит.
